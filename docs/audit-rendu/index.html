1Verdict

Le graphe lui-même est propre et à la bonne taille. Le désordre est autour de lui : les fichiers sont encore rangés selon la séparation « neutre / Vulkan » de l'époque DX12, et le mot Pass veut dire deux choses.

Ce qu'ils ont tous, et ce qu'on ne prend pas

Le motif commun : 4 couches, dépendances vers le bas
  1. Device — l'API : contexte, swapchain, ressources, pipelines.
  2. Graphe — seul dans son coin, ne connaît aucune feature.
  3. Features — une feature = un fichier ou un dossier : son état GPU persistant, et une fonction qui ajoute ses passes, entrées en arguments, sorties en retour.
  4. Ordre de la frame — un seul endroit appelle les features de haut en bas. C'est la table des matières.

Chez nous : 1 et 2 sont en place. 3 est éparpillé, 4 est à moitié là.

Ce qu'on ne copie pas
  • Ressources nommées par chaîne (Granite) : nos handles typés attrapent plus d'erreurs.
  • Blackboard (Frostbite, Filament, Unreal) : à 20 passes, passer les handles en arguments se lit mieux qu'un sac partagé.
  • Culling et aliasing : déjà écartés par le plan (aliasing en option 5.4).
  • Une couche « neutre » : faite et défaite le 2026-10-25, sans second backend elle n'achète rien.

8L'idéal pour Batap

Le motif commun, appliqué tel quel : aucun type nouveau qui ne remplace pas un ancien, aucune couche d'abstraction, le cœur du graphe intact. Ce sont des déplacements, des renommages et trois découpes.

Un mot, un sens

Passe

Un nœud du graphe : graph.addPass("scene"). Rien d'autre ne s'appelle Pass.

Feature

Un struct qui garde un état GPU d'une frame à l'autre et expose addPasses(graph, entrées) → sorties. Avec la frame, c'est le seul à appeler addPass. Modèle : ExposurePass aujourd'hui.

Drawer

Enregistre des draws dans une passe déjà ouverte : pipeline, push, draw. N'inclut jamais RenderGraph.h.

Liste

Ce que le gameplay remplit côté CPU, sans Vulkan : Billboards, DebugDraw, TerrainDraws.

Règles

  • Dossier = rôle. Un coup d'œil à l'arborescence dit qui fait quoi.
  • Nom de fichier = nom du struct principal. Renderer est dans Renderer.h, ResourceManager dans ResourceManager.h.
  • Dépendances vers le bas seulement : Renderer → Scene → Features → Draws → Device, et Features → Graph → Device. Une feature peut utiliser un drawer (les ombres dessinent les meshes) ; deux features ne se connaissent pas : c'est SceneFrame qui passe la sortie de l'une en entrée de l'autre.
  • La racine de Renderer/ = ce que le reste du moteur inclut. Mesuré : 10 en-têtes (Renderer, ResourceManager, SceneBinding, les 3 listes, EngineConfig, ResourceFormat, Tonemap, SkyIrradiance). Les includes hors du rendu ne changent pas.

    const Shadows::Output shadows = shadows_.addPasses(graph, in, draw);
    const SceneImages scene = addScenePass(graph, in, draw, shadows, as, gi);
    exposure_.addPasses(graph, scene.hdr_, constants, draw);
    addTonemapPass(graph, in, draw, scene);
    return true;
}
